## 1. Integration options

| Option | Use it to | Auth |
|---|---|---|
| **REST API**, `/tmf-api/AiM/v4` | Read the catalog, deploy, monitor and stop models | Bearer token (Keycloak) |
| **Webhooks** (TMF Hub), `/tmf-api/AiM/v4/hub` | Be told when a model is created, updated, stopped or deleted through the API | Token to register; callbacks are unauthenticated |
| **Model download**, `/tmf-api/AiM/v4/aiModelSpecification/{id}/artifacts` | Run a catalogued model in your own code instead of calling a deployed endpoint | Bearer token (Keycloak) |
| **MCP server**, `/tmf-api/sse` | Let an AI agent browse the catalog and the deployed models (read-only) | None |
| **Platform plugins** (Java): `CatalogSource`, `ArtifactLocator`, `PlatformDeployer` | Add another model platform (e.g. Kubeflow) or deploy somewhere other than Docker (e.g. KServe); see [section 8](#8-adding-a-model-platform) | n/a |

The OpenAPI document is served at `/tmf-api/v3/api-docs`, and Swagger UI at `/tmf-api/swagger-ui.html`. Of the resources the specification defines, only `aiModel`, `aiModelSpecification` and `hub` are implemented (see [Limitations](#9-limitations)).

## 2. Authentication

The API is an OAuth 2.0 resource server. Send `Authorization: Bearer <access token>` on every request. A request is accepted if all of these hold:

- **Signature:** the token is signed by the Keycloak realm (`openslice`). Keys are fetched from `spring.security.oauth2.resourceserver.jwt.jwk-set-uri`.
- **Issuer:** its `iss` claim **equals** `keycloak.issuer-uri` character for character. Keycloak sets `iss` from the URL the token was requested on, so request tokens from the same address the API is configured with. A mismatch gives `401`, which is the most common integration failure.
- **Validity:** it has not expired.
- **Role:** the realm role `ROLE_USER` is in `realm_access.roles`. Without it, `aiModel` and `aiModelSpecification` calls return `403`.

Get a token with the password grant on the public client `osapiWebClientId`:

```bash
curl -s -X POST "$KEYCLOAK/auth/realms/openslice/protocol/openid-connect/token" \
  -d grant_type=password -d client_id=osapiWebClientId -d username=<user> -d password=<password>
```

For a machine-to-machine integration, ask the Keycloak administrator for a confidential client with a service account that has `ROLE_USER`, and use `grant_type=client_credentials`. The API only checks the token, not which client obtained it. Refresh the token before it expires (`expires_in` in the token response).

## 3. API conventions

| Topic | Behaviour |
|---|---|
| Base URL | `http(s)://<host>:13082/tmf-api/AiM/v4` |
| Request body | `Content-Type: application/json` |
| Null fields | Left out of responses. Treat a missing attribute as null. |
| Paging | `offset` (default 0) and `limit` (default **50**) on list endpoints. Results are ordered by `id`, so pages are stable. No total count is returned: keep fetching until a page has fewer than `limit` items. |
| Attribute selection | `fields=a,b,c` on any GET returns only those top-level attributes, plus `id`, `href` and `@type`. Use it on lists: full specifications are large. |
| Compression | Responses are gzip-compressed when the client sends `Accept-Encoding: gzip`. Most HTTP clients do this automatically. |
| Identifiers | `id` is a UUID generated by the API. `href` is the resource path. |
| PATCH | Changes only the attributes you send. A list you leave out is kept; a list you send replaces the stored one (`[]` clears it). Exception: `serviceCharacteristic` and `specCharacteristic` entries are merged by `name`. |
| Errors | `400` with a plain-text reason (for example an invalid state); a request body that fails validation (for example a missing `software`) gets a JSON `400` whose `errors` list names each field. Unexpected `500` errors carry no message: the detail is in the server log. `401` bad or expired token, `403` missing role, `501` resource not implemented. An unknown id gives `404`, with the reason, on GET, PATCH and DELETE of both resources. Model downloads add `413` and `503` (see [5.2](#52-download)). |

### References between resources

An `aiModel` refers to its specification with a slim reference, not the full object:

```json
"aiModelSpecification": {
  "id": "3f2c…", "href": "/tmf-api/AiM/v4/aiModelSpecification/3f2c…",
  "name": "iris-classifier", "version": "m-8a1e…",
  "@type": "AIModelSpecification", "@baseType": "ServiceSpecification"
}
```

When creating a model, `{"id": "…"}` is enough.

## 4. The deployment contract

### 4.1 Discover

```http
GET /tmf-api/AiM/v4/aiModelSpecification?fields=name,version,description&limit=50
```

Specifications appear automatically when models are logged to MLflow (see the [model publishing guide](MODEL_PUBLISHING_GUIDE.md)). Treat them as read-only, even though `POST`, `PATCH` and `DELETE` exist. Within one `name`, each `version` is a different trained model.

### 4.2 Deploy

```http
POST /tmf-api/AiM/v4/aiModel
Content-Type: application/json

{
  "name": "fraud-scoring-eu-1",
  "state": "reserved",
  "aiModelSpecification": { "id": "<SPEC_ID>" },
  "software": [ { "id": "mlflow" } ],
  "startDate": "2026-12-01T08:00:00Z",
  "endDate":   "2026-12-31T23:59:59Z",
  "serviceCharacteristic": [
    { "name": "platform",   "valueType": "string", "value": "mlflow" },
    { "name": "dockerHost", "valueType": "string", "value": "tcp://10.0.0.5:2375" }
  ]
}
```

| Input | Rule |
|---|---|
| `state` | `reserved` deploys. `designed` or `feasibilityChecked` only create the record. `active`, `inactive` and `terminated` are rejected with `400`. |
| `aiModelSpecification`, `software` | Required (`400` otherwise). For `software`, `[{"id": "mlflow"}]` is enough. |
| `platform` characteristic | **Required to deploy**: it selects the deployer (`mlflow`). Without a matching deployer, the model stays `reserved` and nothing happens. |
| `dockerHost` characteristic | Optional. The Docker daemon to run on. Default: the server's `mlflow.docker.host`. Any other value must be in the server's `mlflow.docker.allowed-hosts`; otherwise `400`. |
| Server-owned characteristics | `containerId`, `imageName`, `hostPort`, `endpoint`, `deployedAt` and `inferencePayloadExample` are written by the server only. If a request contains them (on POST or PATCH), they are dropped without an error, so reading a model and sending it back is safe. |
| `startDate` / `endDate` | Optional. Default: now, and **now + 1 day**. Deployment starts at `startDate`; the model is torn down at `endDate`. Always set `endDate` for long-lived deployments. |
| `name` | Optional. Default: `<specName>-v-<specVersion>-<n>`. |

The response returns immediately (`201`, state `reserved`). The API fills in `mlflowModelId` and related characteristics from the specification.

### 4.3 Wait for the result

Deployment takes from seconds (the image already exists) to several minutes (the image is built). Either subscribe to [webhooks](#6-event-notifications-webhooks), which report the outcome as an `AiModelStateChangeEvent` (`active` or `designed`), or poll:

```http
GET /tmf-api/AiM/v4/aiModel/<MODEL_ID>?fields=state,serviceCharacteristic,note
```

Poll with back-off (for example every 5 s, up to 15 minutes) until `state` is no longer `reserved`:

| Outcome | `state` | Read |
|---|---|---|
| Success | `active` | Characteristics `endpoint` (POST predictions here), `inferencePayloadExample` (request body template), plus `containerId`, `hostPort`, `imageName`, `dockerHost`, `deployedAt` |
| Failure | `designed` | The last entry of `note` (author `TMF915_DeploymentScheduler`) holds the reason. You can retry with `PATCH {"state":"reserved"}`. |

`endpoint` is a plain HTTP URL on the Docker host (or under the operator's `aimodel.deployment.serving-base-url`, if set), served by the MLflow scoring server. It does not go through this API and is not authenticated. Route traffic to it from a trusted network, or put your own gateway in front of it.

### 4.4 Stop, update, delete

| Call | Effect |
|---|---|
| `PATCH /aiModel/<id>` `{"state":"inactive"}` | Stops the container, and removes the image unless another model still uses it. `containerId`, `hostPort`, `endpoint`, `deployedAt` and `inferencePayloadExample` are removed from the model. State becomes `terminated`. |
| `PATCH /aiModel/<id>` with other fields | Updates them. `serviceCharacteristic` entries are merged by `name`. |
| `DELETE /aiModel/<id>` | Undeploys if needed, then deletes the record. |

State changes a client may request with `PATCH`; anything else returns `400`:

| Request | Allowed from | Effect |
|---|---|---|
| `reserved` | `feasibilityChecked`, `designed`, `terminated` | Schedules a deployment. |
| `inactive` | `active`, `reserved` | Stops the deployment, or cancels a scheduled one; state becomes `terminated`. |
| the model's current state | any | No state change; the other fields are updated. |

`active` and `terminated` are set by the server only. There is no implicit redeploy: to redeploy an `active` model, PATCH `inactive`, then `reserved`.

The API restores scheduled work after a restart: `reserved` models are deployed and `active` models keep their teardown at `endDate`.

## 5. Using a model as a library

Instead of calling a deployed endpoint, a client can download a catalogued model's files through the API and load them in its own process. The client needs only an API token: no access to MLflow, MinIO or storage credentials. Downloading is an **extension**: TMF 915 does not define it. The specification advertises it in the standard `attachment` field, so a generic TMF client can find it.

### 5.1 Find downloadable models

Downloadable specifications carry an attachment of `@type` `ModelArtifactAttachment`:

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$API/aiModelSpecification?fields=name,version,attachment"
```

```json
{
  "id": "3f2c…", "name": "iris-classifier", "version": "m-8a1e…",
  "attachment": [{
    "@type": "ModelArtifactAttachment", "@baseType": "Attachment",
    "href": "/tmf-api/AiM/v4/aiModelSpecification/3f2c…/artifacts?format=mlflow-model",
    "attachmentType": "mlflow-model",
    "mimeType": "application/zip",
    "name": "iris-classifier-m-8a1e…-mlflow-model.zip",
    "size": {"amount": 1843921.0, "units": "bytes"},
    "description": "Model files (format mlflow-model, 10 files, 1843921 bytes), downloaded as a zip"
  }, {
    "@type": "ModelArtifactAttachment", "@baseType": "Attachment",
    "href": "/tmf-api/AiM/v4/aiModelSpecification/3f2c…/artifacts?format=onnx",
    "attachmentType": "onnx",
    "mimeType": "application/zip",
    "name": "iris-classifier-m-8a1e…-onnx.zip",
    "size": {"amount": 412233.0, "units": "bytes"},
    "description": "Model files (format onnx, 1 file, 412233 bytes), downloaded as a zip"
  }]
}
```

| Field | Meaning |
|---|---|
| `href` | The download URL for this format (below). |
| `attachmentType` | The format of the files: how to load them (see [5.3](#53-formats)). There is one attachment per format the model is offered in; the primary one is also in the `artifactFormat` characteristic. |
| `size` | Total size of the files before zipping. `amount` is a TMF float; the exact byte count is in `description`. |
| `name` | A file name for the zip. |

A model is offered as `onnx` too when its publisher added an ONNX copy (see the [model publishing guide](MODEL_PUBLISHING_GUIDE.md#also-offer-an-onnx-version)). A specification has no such attachment when its model cannot be downloaded: its platform does not support downloads, its publisher opted out (characteristic `downloadable=false`), its files are outside the storage the server may read, it is larger than the server's limit, or the server has no storage configured. Specifications catalogued before downloads existed get the attachment in the background after the server's next start.

### 5.2 Download

```bash
curl -fSL -H "Authorization: Bearer $TOKEN" -o iris.zip "$API/aiModelSpecification/<SPEC_ID>/artifacts"
unzip -q iris.zip -d iris-model

# Another format the specification offers (an attachmentType of its attachments)
curl -fSL -H "Authorization: Bearer $TOKEN" -o iris-onnx.zip "$API/aiModelSpecification/<SPEC_ID>/artifacts?format=onnx"
```

Without `format`, the download is the primary format (`artifactFormat`). The simplest client follows an attachment's `href`, which always names its format.

| Status | Meaning |
|---|---|
| `200` | `Content-Type: application/zip`, `Content-Disposition: attachment; filename="<name>-<version>.zip"` (`<name>-<version>-<format>.zip` with `format`). The zip is streamed while the server reads the files from storage, so there is no `Content-Length`. Entry names are paths relative to the model directory; none is absolute or contains `..`. |
| `400` | `format` is not made of letters, digits, `.`, `_` and `-` (at most 64). |
| `401`, `403` | No valid token, or no `ROLE_USER`. Every user with `ROLE_USER` may download every downloadable model. |
| `404` | Unknown id, no downloadable files, or not offered in that `format`. The plain-text body says which, and says when the publisher opted out (`downloadable=false`). It does not say whether files exist outside the allowed storage. |
| `413` | Larger than the server's limit (`aimodel.artifacts.max-download-bytes`, 2 GB by default). The limit applies per format: the `onnx` download of a large model may still fit. |
| `503` | Storage is temporarily unavailable. Retry later. |

**Time limit.** A download that takes longer than `aimodel.artifacts.download-timeout` (15 minutes by default) is cut off. The client then has an incomplete zip, which `unzip -t` rejects. Errors after the first bytes have been sent cannot change the `200` status, so always check the zip, for example by comparing the extracted size with `size`. There is no resume (`Range`) support; download again.

Every download is logged on the server with the user (token subject), the specification, the format and the bytes sent.

### 5.3 Formats

| `attachmentType` / `artifactFormat` | Content | Load with |
|---|---|---|
| `mlflow-model` | An MLflow model directory: `MLmodel`, environment files (`requirements.txt`, `conda.yaml`, `python_env.yaml`) and the flavor's files | `mlflow.pyfunc.load_model(<directory>)`, after installing `requirements.txt` |
| `onnx` | `model.onnx`, a self-contained ONNX model (offered when the publisher added one) | [ONNX Runtime](https://onnxruntime.ai/), in Python, Java, C#, C++, JavaScript, … No ML framework or MLflow needed |
| others (e.g. `pytorch`, `tensorflow-savedmodel`, `huggingface`) | As the platform stores them | The framework's own loader |

The API delivers the files as the platform stored them; it does not convert between formats. New platforms add rows to this table; existing values keep their meaning.

### 5.4 Example: load an MLflow model in Python

```python
import os, subprocess, sys, zipfile
import pandas as pd
import requests

API = "http://localhost:13082/tmf-api/AiM/v4"
TOKEN = os.environ["TOKEN"]
SPEC_ID = "<SPEC_ID>"

# Stream to a file: models can be large.
with requests.get(f"{API}/aiModelSpecification/{SPEC_ID}/artifacts",
                  headers={"Authorization": f"Bearer {TOKEN}"}, stream=True, timeout=60) as r:
    r.raise_for_status()
    with open("model.zip", "wb") as f:
        for chunk in r.iter_content(chunk_size=1 << 20):
            f.write(chunk)

with zipfile.ZipFile("model.zip") as z:
    assert z.testzip() is None        # fails on a cut-off download
    z.extractall("model")

# The model's own dependencies, ideally in a fresh virtual environment.
subprocess.run([sys.executable, "-m", "pip", "install", "-r", "model/requirements.txt"], check=True)

import mlflow
model = mlflow.pyfunc.load_model("model")
print(model.predict(pd.DataFrame([[5.1, 3.5, 1.4, 0.2]],
      columns=["sepal length (cm)", "sepal width (cm)", "petal length (cm)", "petal width (cm)"])))
```

The column names come from the model's signature, which `MLmodel` lists under `signature`.

### 5.5 Example: run the ONNX version

```python
import io, zipfile
import numpy as np
import onnxruntime as ort          # pip install onnxruntime; no scikit-learn or MLflow
import requests

r = requests.get(f"{API}/aiModelSpecification/{SPEC_ID}/artifacts", params={"format": "onnx"},
                 headers={"Authorization": f"Bearer {TOKEN}"}, timeout=60)
r.raise_for_status()
with zipfile.ZipFile(io.BytesIO(r.content)) as z:
    z.extract("model.onnx", "model")

session = ort.InferenceSession("model/model.onnx")
features = np.array([[5.1, 3.5, 1.4, 0.2]], dtype=np.float32)
print(session.run(None, {session.get_inputs()[0].name: features})[0])   # predicted labels
```

The input name, type and shape are in `session.get_inputs()`; the outputs depend on the converter (for scikit-learn classifiers: labels, then probabilities).

### 5.6 Security notes

- **Loading a model runs its code.** Pickle, cloudpickle and some other formats execute code when loaded, and `requirements.txt` installs packages. (An ONNX file is a computation graph, not code, which makes `onnx` the safer format to consume.) The API cannot make that safe. Load only models from publishers you trust, in an isolated environment. The server logs who downloaded which model.
- **Publishers decide.** A model whose publisher set `downloadable=false` (see the [model publishing guide](MODEL_PUBLISHING_GUIDE.md#3-what-ends-up-in-the-catalog)) cannot be downloaded through the API.
- **Storage stays private.** The API reads only locations under `aimodel.artifacts.allowed-locations` (the MLflow bucket by default), even for specifications created with `POST /aiModelSpecification` that point elsewhere. Storage credentials never leave the server.

## 6. Event notifications (webhooks)

**Off by default.** The server only sends notifications when `hub.webhook.enabled=true` (environment variable `HUB_WEBHOOK_ENABLED=true`). Registration works either way, but while it is off nothing is delivered and the server logs a warning. Check with the operator before relying on it.

### Register and unregister

```http
POST /tmf-api/AiM/v4/hub
Content-Type: application/json
Authorization: Bearer <token>

{ "callback": "https://oss.example.com/tmf915/events",
  "query": "eventType=AiModelStateChangeEvent,AiModelDeleteEvent" }
```

The response is `201` with the subscription `id`. Unregister with `DELETE /tmf-api/AiM/v4/hub/<id>`. Subscriptions are global, and there is no endpoint to list them.

The `callback` must be an absolute `http` or `https` URL. By default the server resolves its host and refuses (`400`, with the reason) any address it should not send requests to: loopback, link-local (including cloud metadata at `169.254.169.254`), private networks (`10/8`, `172.16/12`, `192.168/16`, IPv6 `fc00::/7`), carrier-grade NAT and unspecified addresses. The check is repeated before every delivery. If your receiver is on an internal network, the operator lists its host in `hub.webhook.allowed-callback-hosts`. When that list is set, only the hosts on it are accepted.

### Filter

`query` is a list of `key=value` conditions separated by `&`. A value may list alternatives separated by commas. All conditions must match. Without a `query`, you receive everything.

| Key | Matches |
|---|---|
| `eventType` | `AiModelCreateEvent`, `AiModelStateChangeEvent`, `AiModelAttributeValueChangeEvent`, `AiModelDeleteEvent` |
| `event.aiModel.id` | One model |
| `event.aiModel.state` | The model's state after the event (`reserved`, `active`, `designed`, `terminated`, …) |

An unknown key never matches, so a typo silences the subscription instead of sending you every event.

### Notification

The server POSTs to your callback with `Content-Type: application/json`:

```json
{
  "eventId": "9b0e…",
  "eventTime": "2026-12-01T08:03:12.481+00:00",
  "eventType": "AiModelStateChangeEvent",
  "event": { "aiModel": { "id": "…", "state": "active", "serviceCharacteristic": [ … ], … } }
}
```

Dates are ISO-8601 strings. Unlike API responses, the `aiModel` here also includes null attributes.

### Delivery semantics

- **Best effort.** One attempt per event and subscriber, with no retries. If your endpoint is down, you miss the event; reconcile by polling (`GET /aiModel?fields=state`) after an outage.
- **Timeouts:** 2 s to connect and 5 s to respond. Answer `2xx` immediately and process asynchronously.
- **Ordering:** subscribers are notified in parallel, and the order of events is not guaranteed. Use `eventTime` and the model's current `state`.
- **Duplicates:** an event can arrive twice; deduplicate on `eventId`.
- **Overload:** under heavy load (more than 1000 pending deliveries), notifications are dropped and logged.
- **No authentication:** notifications are not signed. Expose the callback only to the API's network, or include a hard-to-guess token in the callback URL.

### Which changes produce an event

| Change | Event | `aiModel.state` in the event |
|---|---|---|
| `POST /aiModel` | `AiModelCreateEvent` | as created (`reserved`, `designed`, …) |
| `POST` or `PATCH` with `state: reserved` | `AiModelStateChangeEvent` | `reserved` (deployment scheduled) |
| `PATCH` with `state: inactive` | `AiModelStateChangeEvent` | `terminated` |
| `PATCH` with other fields | `AiModelAttributeValueChangeEvent` | unchanged |
| `DELETE /aiModel/<id>` | `AiModelDeleteEvent` | as before deletion |
| Deployment finished (background) | `AiModelStateChangeEvent` | `active`, with `endpoint` and `inferencePayloadExample` |
| Deployment failed (background) | `AiModelStateChangeEvent` | `designed`, with the reason in the last `note` |
| Teardown at `endDate` (background) | `AiModelStateChangeEvent` | `terminated` |

A deployment that finishes after the model was stopped or deleted is removed again and produces no event; the stop or delete already did. Because delivery is best effort, poll after an outage of your receiver (see [4.3](#43-wait-for-the-result)).

## 7. MCP server for AI agents

The API includes a [Model Context Protocol](https://modelcontextprotocol.io/) server, so AI agents can look up models without custom code. It uses the **SSE transport**:

1. `GET /tmf-api/sse` opens the event stream. The first event (`endpoint`) contains the message URL, `/tmf-api/mcp/message?sessionId=…`.
2. Send JSON-RPC requests (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`) as `POST` to that URL. Responses arrive on the event stream.

| Tool | Arguments | Returns |
|---|---|---|
| `listAvailableAiModelSpecifications` | `offset`, `limit` | `id`, `name`, `version`, `lifecycleStatus`, `href` per specification |
| `getAiModelSpecification` | `specificationId` | One specification summary |
| `listAvailableAiModels` | `namePrefix` (optional) | `id`, `name`, `state`, `version`, `aiModelSpecificationId`, `href` per model |
| `getAiModel` | `modelId` | One model summary |

The tools are read-only: agents cannot deploy or stop models through MCP.

**The MCP endpoints require no token.** This is deliberate, so agents can connect without OAuth, but it means anyone who can reach the API port can read the catalog and the deployed models' ids, names and states. Do not expose `/tmf-api/sse` and `/tmf-api/mcp/` beyond the network your agents run in: either keep the API port off untrusted networks, or block those paths at your reverse proxy. For example, with nginx in front of the API:

```nginx
location ~ ^/tmf-api/(sse|mcp/) {
    allow 10.0.0.0/8;      # the network your agents run in
    deny  all;
    proxy_pass http://tmf915:13082;
    proxy_buffering off;   # SSE
}
```

The API logs a warning about this at every start.

Working Python clients are in [`scripts/`](../scripts/):

```bash
python3 scripts/mcp_sample_client.py --base-url http://localhost:13082/tmf-api
python3 scripts/mcp_interactive_lookup_client.py --base-url http://localhost:13082/tmf-api
```

## 8. Adding a model platform

MLflow is the only platform today. A platform plugs in through three interfaces, each chosen at runtime; the controllers, the scheduler, the sync loop and the download endpoint stay as they are. A complete plugin, for example for Kubeflow, has:

| Piece | Interface | Needed for | MLflow example |
|---|---|---|---|
| Catalog source | `catalog.CatalogSource` | Publishing the platform's models as specifications | `MlflowCatalogSource` (+ `MlflowSpecificationService` for the mapping) |
| Artifact locator (+ store) | `artifacts.ArtifactLocator`, `artifacts.ArtifactStore` | Downloads (section 5) | `MlflowArtifactLocator`, `S3ArtifactStore` |
| Deployer | `deployment.PlatformDeployer` | Deploying the models | `MlflowDeployer` |

Downloads do not need a deployer, and deployment does not need a locator. All three select their models by the `platform` characteristic: the catalog source's `platform()` value.

### 8.1 Catalog source

```java
public interface CatalogSource<T> {
    String platform();                                        // "kubeflow": the platform characteristic
    String artifactFormat();                                  // default format of its models, e.g. "onnx"
    List<DiscoveredModel<T>> discover(Long createdAfterMs);   // null: all models
    boolean hasArtifacts(DiscoveredModel<T> model);           // files stored yet?
    AiModelSpecificationCreate toSpecification(DiscoveredModel<T> model) throws IOException;
}

record DiscoveredModel<T>(String key, String name, String version, long createdAtMs, T details) {}
```

Make it a bean, `@ConditionalOnProperty` on your platform's `…enabled` setting. `CatalogSyncService` runs every source on the schedule `aimodel.catalog.sync.interval-ms` and does the generic work, so the source only talks to its platform:

- **`discover`:** with `null`, list all models; with a time, at least the models created after it (more is allowed). Fill `name` and `version` as the specification's: together they decide whether the model is already in the catalog. `key` must be unique within your source. Set `createdAtMs` if your platform can search by creation time; the sync then asks for new models only, and searches in full every `aimodel.catalog.sync.full-interval-ms`. Use `0` if it cannot. If an incremental search throws, the sync stops trying them and searches in full. `details` is yours: whatever `hasArtifacts` and `toSpecification` need.
- **`hasArtifacts`:** `false` makes the sync skip the model and check again after 10 minutes.
- **`toSpecification`:** name, version, description, `lifecycleStatus` and the characteristics your locator and deployer need (for example the artifact location). Do **not** add `platform`, `artifactFormat` or the download attachment: the sync adds them for every source. Set `artifactFormat` yourself only if a model's format differs from `artifactFormat()`. To honour a publisher's opt-out, set the characteristic `downloadable=false`, as the MLflow source does from the tag `downloadable`.

The sync remembers which models it published, never creates one twice, processes newer models first, and logs and skips a model or source that fails.

### 8.2 Downloads: artifact locator and store

1. An `ArtifactLocator` bean: `supports(spec)` checks the `platform` characteristic; `locate(spec)` returns one `ArtifactLocation` per format the model may be offered in, primary first: a URI, the format, and optionally the exact files that make it up. It must not read storage: formats whose files are missing are simply not offered. `MlflowArtifactLocator` (the MLflow directory, plus `extra_files/model.onnx` as `onnx`) is the example.
2. An `ArtifactStore` for the location's URI scheme, if it is not `s3://` (`S3ArtifactStore`): it lists the files under a location and opens one. Add your locations to `aimodel.artifacts.allowed-locations`.

The endpoint, roles, allow-list, size and time limits, zip streaming, logging and the attachment on synced specifications are generic.

### 8.3 Deployer

Deployment is platform-agnostic. The lifecycle service and the scheduler handle states, dates, scheduling and restarts, and delegate the actual work to `PlatformDeployer` beans. MLflow-on-Docker (`MlflowDeployer`) is the only implementation today.

```java
public interface PlatformDeployer {
    boolean supports(AiModel model);                                  // e.g. platform characteristic == "kserve"
    List<Characteristic> deploy(AiModel model) throws IOException;    // start serving; return endpoint and IDs
    void undeploy(AiModel model);                                     // stop serving and free resources
    default void validateCharacteristics(List<Characteristic> c) {}   // reject client input with 400
}
```

To add one, for example KServe:

1. Create `integrations/kserve/KServeDeployer implements PlatformDeployer`, annotated `@Service` and `@ConditionalOnProperty("kserve.enabled")`.
2. **`supports`:** return true when the model's `platform` characteristic is your value (`kserve`). Clients select your platform by sending that characteristic.
3. **`deploy`** runs on a scheduler thread, **outside any database transaction**, with a detached copy of the model. It may take minutes; no database connection is held meanwhile.
   - Read your inputs from the model's `serviceCharacteristic`, and from its specification's `specCharacteristic` (for example `artifactUri` or `loggedModelId`).
   - Start the deployment and wait until it serves.
   - **Return** the characteristics to record: an `endpoint`, and any IDs you need to undeploy later. Do not write the model. The scheduler stores them and sets `active` in a short transaction, and publishes the state-change event.
   - If the model was stopped or deleted while you were deploying, the scheduler calls your `undeploy` with the returned characteristics instead, so nothing is left running.
   - **Throw** on failure, preferably a `DeploymentException` with a short, client-safe reason. The scheduler sets the model to `designed` and shows only that reason in `note`; the full exception goes to the server log.
4. **`undeploy`:** release everything using the IDs you stored, after checking that they still belong to this model: characteristics in old rows may have been written by clients. `MlflowDeployer` does this with a container label (`tmf915.aiModelId`). Remove the deployment's characteristics from the model. Do not change the state; the caller sets `terminated`. Make it safe to call twice.

See `MlflowDeployer` for a complete example.

## 9. Limitations

- **Implemented resources:** only `aiModel`, `aiModelSpecification` and the event subscription `hub` (`POST /hub`, `DELETE /hub/{id}`). AI contracts, contract specifications and violations, alarms, rules, monitors, topics and events return `501 Not Implemented`. So does the topic-scoped hub, `/topic/{id}/hub`.
- **Webhooks:** off by default, best effort, no retries and no signing (see [section 6](#6-event-notifications-webhooks)).
- **Model endpoints:** they are plain HTTP and unauthenticated (see [4.3](#43-wait-for-the-result)).
- **Model downloads:** MLflow models are offered as `mlflow-model`, and as `onnx` when the publisher added an ONNX copy; the API does not convert. No resume, and a time limit per download (see [section 5](#5-using-a-model-as-a-library)).
- **MCP:** unauthenticated by design; restrict it at the network level (see [section 7](#7-mcp-server-for-ai-agents)).
- **Specification lists:** no total count is returned.
