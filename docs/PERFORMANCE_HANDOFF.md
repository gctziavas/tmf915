# Performance work handoff: TMF915 AI Management API

This is a brief for an engineer or coding agent picking up performance work on this repository with no prior context. It states what is wrong, what has been verified, what to change, and how to know each change worked.

## Goal

Make the API cheaper to call, starting with `GET /tmf-api/AiM/v4/aiModel` ("List Existing AI Models" in the Postman collection). That endpoint returns huge payloads because each `AiModel` embeds its whole `AiModelSpecification` instead of a reference to it.

Work through Part 1 first. It fixes the payload problem and is the only part the owner has explicitly asked for. Parts 2 and 3 are further improvements in priority order; do them only if asked, or stop and report after Part 1.

## Project facts

- Spring Boot 4.0.3, Java 17, Maven, Spring Data JPA (Hibernate), MySQL in production, H2 in tests.
- Base package: `org.etsi.osl.controllers.tmf915` under `src/main/java`.
- `model/` classes were generated by OpenAPI Generator but are hand-edited (JPA annotations, custom serializer). Edit them directly; do not regenerate.
- Run unit tests with `mvn test`. Integration tests (`*IntegrationTest`) are excluded from `mvn test` and need external MLflow/Docker, so do not rely on them.
- The working tree has uncommitted changes that add an MCP server (`pom.xml`, `application.yml`, `OpenApiGeneratorApplication.java`, `SecurityConfiguration.java`, `AiModelRepositoryService.java`, plus untracked `mcp/` and `scripts/`). They are the owner's work in progress. Keep them, and do not commit or push unless asked.

## The root cause (verified)

`AiModel.getAiModelSpecification()` is annotated to serialize as a slim reference:

```java
// src/main/java/org/etsi/osl/controllers/tmf915/model/AiModel.java, around line 476
@JsonProperty("aiModelSpecification")
@JsonSerialize(using = AiModelSpecificationRefSerializer.class)
public @Nullable AiModelSpecification getAiModelSpecification() {
```

The annotation is `com.fasterxml.jackson.databind.annotation.JsonSerialize`, which belongs to Jackson 2. Spring Boot 4 serializes HTTP responses with Jackson 3 (`tools.jackson.*`), which does not read Jackson 2 databind annotations. The serializer is therefore ignored and the full specification is written. Annotations from `jackson-annotations` such as `@JsonProperty` and `@JsonIgnore` are shared by both versions and keep working, which is why nothing else looks broken.

Both Jackson versions are on the classpath (`jackson-databind-3.0.4` and `jackson-databind-2.20.2`).

This was reproduced by serializing one `AiModel` holding a specification with both mappers, against the built classes:

- `tools.jackson.databind.json.JsonMapper.builder().build()` wrote the full specification, including `specCharacteristic` and `modelDataSheet`.
- `new com.fasterxml.jackson.databind.ObjectMapper()` wrote `"aiModelSpecification":{"id":"spec-1","name":"n","version":"1"}`.

The existing test `testAiModelSpecificationSerializesAsReference` in `src/test/java/org/etsi/osl/controllers/tmf915/model/AiModelUnitTest.java` passes because it constructs a Jackson 2 `ObjectMapper` by hand. It does not cover the HTTP path.

Not verified: the running application was never called. That the HTTP layer uses Jackson 3 is inferred from Spring Boot 4 defaults and the jar contents. Task 1.2 confirms it.

### 1.2 Add a test through the real HTTP path

### 1.3 Build the reference without loading the specification

`aiModelSpecification` is `@ManyToOne(fetch = LAZY)`. After 1.1, the serializer calls `getName()` on the lazy proxy, which loads one full specification row per model (about 15 JSON TEXT columns each). For a list of N models that is N extra queries.

The `aim915_aim` row already stores what the reference needs, in the embedded `serviceSpecification` (`ServiceSpecificationRef`, columns `svc_spec_id`, `svc_spec_name`, `svc_spec_version`, `svc_spec_href`), which `AiModelRepositoryService.normalize` fills from the specification. That getter is `@JsonIgnore`.

Preferred approach: have the JSON `aiModelSpecification` property written from the stored reference fields when they are present, and only fall back to the entity when they are not. Getting the specification id from an uninitialized Hibernate proxy does not trigger a load, so `id` and a derived `href` (`/tmf-api/AiM/v4/aiModelSpecification/{id}`) are always available cheaply.

Acceptable alternative if that proves awkward: fetch the specification with the list in one query (`@EntityGraph` or `JOIN FETCH`). It removes the N+1 but still reads every specification's blobs.

Note that `normalize` currently skips an uninitialized specification (`Hibernate.isInitialized` check, an uncommitted change). Keep that behaviour; it exists so listing does not force a load.

Done when: listing N models issues no per-model query against `aim915_aimspec`. Check with `spring.jpa.show-sql` or Hibernate statistics in a test.

### 1.4 Honour `offset` and `limit`

`AiModelApiController.listAiModel(fields, offset, limit)` ignores all three arguments and calls `repoService.findAllAiModels()`, which returns every row. The Postman request sends `limit={{listLimit}}` to no effect.

Add paging to `AiModelRepositoryService` with a default limit of 50, matching `AiModelSpecificationRepositoryService.findAllAiModelSpecifications`. `AiModelRepository` already extends `PagingAndSortingRepository`.

Do not copy the specification service's offset arithmetic as is: `PageRequest.of(offset / size, size)` returns the wrong window when `offset` is not a multiple of `limit`. Use an offset-based `Pageable` (or fix both services the same way) and add a stable sort so pages do not overlap.

`findAllAiModels()` has other callers (`AiCatalogMcpTools`, `AiModelLifecycleService`). Keep an unpaged method for them or update them.

Implementing `fields` is optional for Part 1. If skipped, say so in the report.

### 1.5 Batch the characteristic load

`AiModel.serviceCharacteristic` is a lazy `@OneToMany` and is loaded during serialization, one query per model. Add `@BatchSize(size = 50)` on the collection, or set `spring.jpa.properties.hibernate.default_batch_fetch_size: 50` in `application.yml`. The global setting also helps `AiModelSpecification.specCharacteristic`.

## Part 2: database and persistence

Ordered by expected benefit. Each is independent.

1. **Specification list is heavy.** `GET /aiModelSpecification` returns every JSON TEXT column for each row plus a lazy `specCharacteristic` query per specification. Implement the `fields` query parameter, or return a light projection (id, href, name, version, lifecycleStatus, description, lastUpdate) for the list and keep the full entity for get-by-id. Changing the default list shape is an API behaviour change, so confirm with the owner before doing so.
2. **Null fields and compression.** The Jackson 3 output writes every null field. Set non-null property inclusion and `server.compression.enabled: true` with JSON in the mime types. Excluding nulls changes output on every endpoint and may break tests or clients that expect explicit nulls; check before applying.
3. **Missing indexes.** Add indexes on `aim915_aim(state)`, `aim915_aim(name)` and `aim915_aimspec(name, version)` via `@Table(indexes = ...)`. The schema is managed by `ddl-auto: update`. The last index serves `findByNameAndVersion`, which the MLflow sync calls per model.
4. **Open session in view.** `spring.jpa.open-in-view` is at its default (on), so lazy loads run during response serialization and hold a connection for the whole request. Set it to `false` and put `@Transactional(readOnly = true)` on read methods in the two `reposervices` classes. Do this after Part 1, since turning it off will surface any remaining lazy access as `LazyInitializationException`; the test suite should catch these.
5. **Converter cost on read.** About 25 columns across `AiModel` and `AiModelSpecification` use JSON `AttributeConverter`s (`mappers/converters`). Each is parsed on load, and Hibernate is believed to copy mutable converted values through the converter again for dirty checking. This second cost is an assumption; measure with a profiler before optimizing. Read-only transactions and projections on list paths are the cheap mitigation.
6. **Load-to-count.** `AiModelLifecycleService.deriveUniqueName` loads every model whose name starts with a prefix only to call `size()`. Replace with a `countByNameStartingWith` repository method.
7. **Payload logging.** `log.info("AiModel CREATE: {}", aiModelCreate)` and the equivalent in the specification service stringify whole objects at INFO on every create. Log ids and names, or move to DEBUG.

### Test configuration

`src/test/resources/application.yml` was replaced by `src/test/resources/application.properties`. A YAML file with the same name in test resources shadows the main `application.yml` on the classpath, so the tests ran without production settings and had to repeat them. A `.properties` file is loaded alongside the main YAML and takes precedence on conflicts. Tests therefore run with the real `application.yml`, overridden only for H2, `ddl-auto: create-drop`, the H2 dialect, and no MLflow (sync off, unreachable tracking URI). Profile files such as `application-integration.yml` still apply on top.

Consequences:

- `AiModelListHttpTest` and `ResponseCompressionTest` no longer repeat settings from `application.yml`. `open-in-view`, null exclusion and compression are now checked against the real file.
- MockMvc requests carry the real context path (`/tmf-api`), because `server.servlet.context-path` and `openapi.aiManagement.base-path: /AiM/v4` now apply.
- Integration tests (`@ActiveProfiles("integration")`) now also get the main `application.yml`. Before, they lacked `springdoc.oAuthFlow.*` and `jwt.jwk-set-uri`, which are required at startup, so they most likely could not start. A throwaway test confirmed that the integration-profile context now starts with the expected values (H2, `create-drop`, integration port range, main springdoc settings). The integration tests themselves were not run, because they need the remote MLflow and Docker hosts.

## Part 3: MCP tools, MLflow sync, webhooks

1. **MCP lookups scan everything.** In `mcp/AiCatalogMcpTools.java`, `getAiModel` loads all models and filters in memory, and `getAiModelSpecification` pages through all full specifications. Use `findAiModelById` and `findAiModelSpecificationById`.
2. **Classic-registry sync has no cache.** In `integrations/mlflow/MlflowSyncService.java`, `syncFromLoggedModels` keeps a synced set and a missing-artifact back-off; `syncFromClassicRegistry` does a database lookup and an artifact check for every version every 60 seconds. Apply the same two caches.
3. **Full MLflow fetch each cycle.** Every sync fetches all logged models. Filter by creation time since the last successful sync if the MLflow search API allows it, or lengthen `mlflow.sync.interval-ms`.
4. **Webhook delivery.** `integrations/hub/WebhookDispatcher.java` builds a `RestClient` with no connect or read timeout (its `timeout()` method is never used) and delivers to subscribers one after another. Add timeouts and deliver in parallel so one slow subscriber does not delay the rest.
5. **Async executor.** `@EnableAsync` is on with no explicit executor configuration. Define a bounded executor for webhook delivery.

## Part 4: findings from the documentation review

These were found while rewriting `README.md` and the guides in `docs/` (2026-11-26) and checking every statement against the code and a running instance. They are mostly correctness and configuration problems, not performance. **None is fixed.** The guides describe the current behaviour, so each item lists the documentation to update once it is fixed.

Ordered by impact. Items 4.3 and 4.8 change who can access what: do not implement them without the owner's decision.

### 4.1 Webhooks never report deployment outcomes (high)

**Problem.** `AiModelDomainEvent`s are only published by `AiModelLifecycleService`, in response to API calls. State changes made in the background by `DeploymentScheduler` publish nothing:

- deployment completed: `reserved` → `active` (`MlflowModelService.updateModelAfterDeploy`);
- deployment failed: → `designed`, with a note (`DeploymentScheduler.executeDeployment`, catch block);
- automatic teardown at `endDate`: → `terminated` (`DeploymentScheduler.executeUndeploy`).

So a subscriber never learns that its model became `active`, which is the main reason to subscribe. The old integration guide's example (waiting for `active` in a webhook) could never fire.

**Fix.**

1. Inject `ApplicationEventPublisher` into `DeploymentScheduler`.
2. Publish `AiModelDomainEvent(model, STATE_CHANGE)` with the reloaded model after `executeDeployment` (state `active` or `designed`) and after `executeUndeploy` (state `terminated`).
3. Publish **after** the `TransactionTemplate` has committed, outside the lambda, so listeners never see uncommitted state.
4. Publishing is cheap when webhooks are disabled (no listener).

**Verify.** A unit test in the style of `DeploymentSchedulerTest` with a mocked publisher: one event per outcome, with the right state.

**Docs to update.** `docs/INTEGRATION_GUIDE.md`:

- section 4.3: polling no longer required;
- section 5, "Which changes produce an event": add the three background rows and remove the "send no event" paragraph;
- section 8, Limitations.

### 4.2 Docker Compose rejects every token on a new machine (high)

**Problem.** `docker-compose.yml` hard-codes `KEYCLOAK_ISSUER_URI` and `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI` to `http://172.16.100.94:8080/auth/realms/openslice`. `SecurityConfiguration.jwtDecoder()` accepts a token only if its `iss` equals that string exactly, and Keycloak sets `iss` from the URL it was called on. On any other machine every API call returns `401` until someone edits the file.

The `MLFLOW_*` defaults point at the same lab host, but those are already overridable with `${…:-…}`.

**Fix.**

- Make both issuer lines `${KEYCLOAK_ISSUER_URI:-http://localhost:8080/auth/realms/openslice}`.
- Consider the same `localhost` default for the MLflow and MinIO URLs, so the `full` profile works without exports.

**Verify.** On a fresh machine: `docker compose --profile full up -d --build`, get a token from `localhost:8080`, call `GET /tmf-api/AiM/v4/aiModel` and expect `200`.

**Docs to update.** `docs/USER_GUIDE.md` section 1.1 (becomes "set `KEYCLOAK_ISSUER_URI` if clients use another address") and the note under "Quick start" in `README.md`.

### 4.3 MCP endpoints are unauthenticated (owner decision)

**Problem.** `SecurityConfiguration` permits `/mcp/**` and `/sse/**` without a token, so anyone who can reach the API can list the catalog and the deployed models' names, states and ids through the MCP tools. This was confirmed on a running instance. The tools are read-only.

**Options.**

- **(a)** Require a bearer token: remove the two paths from `permitAll`, and update `scripts/mcp_*.py` to send `Authorization`.
- **(b)** Keep it open and restrict it at the network level.
- **(c)** Keep it open, and document it as intentional.

The guides currently describe (c) as a warning.

**Docs to update.** `docs/INTEGRATION_GUIDE.md` sections 1 and 6, and the `README.md` "What it does" list.

### 4.4 Spec PATCH/DELETE of an unknown id returns 500 (medium)

**Problem.** `AiModelSpecificationRepositoryService` throws `IllegalArgumentException("No AiModelSpecification with ID …")`, and `AiModelSpecificationApiController` has no `@ExceptionHandler`, so the client gets `500`. `AiModelApiController` maps the same exception to `400`, which is also wrong for "not found".

**Fix.** Return `404` for unknown ids in both controllers, and keep `400` for invalid input (for example a forbidden state).

- Use a dedicated exception, or check existence first.
- Do **not** use a `@ControllerAdvice`: springdoc 2.6.0 breaks with one (see "Further notes" in the Part 3 outcome). Use a per-controller `@ExceptionHandler`, as `AiModelApiController` already does.
- Changing `aiModel` from `400` to `404` is visible to clients; mention it in the release notes.

**Verify.** MockMvc tests in `AiModelListHttpTest`: PATCH and DELETE of an unknown id on both resources return `404`.

**Docs to update.** `docs/INTEGRATION_GUIDE.md` section 3, "Errors" row.

### 4.5 Synced specifications have no `lifecycleStatus` (low)

Specifications created by the MLflow sync have no `lifecycleStatus`. The MCP tool `listAvailableAiModelSpecifications` returns `null` for it, and the Postman request "2. **Verify.** Extend `MlflowSpecificationService` tests.

### 4.6 `aimodel.deployment.serving-base-url` is not used (low)

**Problem.** It is defined in `application.yml` and set from `docker-compose.yml` (`AIMODEL_DEPLOYMENT_SERVING_BASE_URL`), but no code reads it. Meanwhile the `endpoint` characteristic uses the Docker host's address, which is `localhost` for a Unix socket (`MlflowDeploymentService.resolveEndpointHost`). That endpoint is only reachable on the Docker machine, which is the case in the default Compose setup.

**Options.**

- **(a)** Implement it: when set, build `endpoint` as `<serving-base-url>:<hostPort>/invocations`.
- **(b)** Delete it from both files.

(a) fixes a real usability problem.

**Docs to update.** `docs/USER_GUIDE.md` section 5 and the troubleshooting row "`endpoint` not reachable", and `docs/MODEL_PUBLISHING_GUIDE.md` section 5.

### 4.7 `full` profile needs a manual MinIO bucket (low)

**Problem.** The `mlflow` service stores artifacts in `s3://mlflow/`, but nothing creates the `mlflow` bucket in MinIO. Artifact uploads fail until someone creates it in the console.

The user guide states this, based on MLflow and MinIO behaviour; it was not reproduced here.

**Fix.** Add a one-shot `minio-init` service to the `full` profile (image `minio/mc`) that waits for MinIO and runs `mc mb --ignore-existing local/mlflow`. Make `mlflow` depend on it.

**Docs to update.** `docs/USER_GUIDE.md` section 1.2: remove the manual step.

### 4.8 Model endpoints are unauthenticated (owner decision)

**Problem.** The `endpoint` of an active model is the MLflow scoring server on a published host port (3000–7000), reachable without credentials. This is the platform's design rather than a bug, and both guides document it.

**Options.**

- Bind containers to an internal network and put an authenticating gateway in front.
- Add an inference proxy to this API (for example `POST /aiModel/{id}/invocations`) that checks the token and forwards the request.
