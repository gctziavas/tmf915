# Performance work handoff: TMF915 AI Management API

This is a brief for an engineer or coding agent picking up performance work on this repository with no prior context. It states what is wrong, what has been verified, what to change, and how to know each change worked.

## Goal

Make the API cheaper to call, starting with `GET /tmf-api/AiM/v4/aiModel` ("List Existing AI Models" in the Postman collection). That endpoint returns huge payloads because each `AiModel` embeds its whole `AiModelSpecification` instead of a reference to it.

Work through Part 1 first. It fixes the payload problem and is the only part the owner has explicitly asked for. Parts 2 and 3 are further improvements in priority order; do them only if asked, or stop and report after Part 1.

## The root cause (verified)

`AiModel.getAiModelSpecification()` is annotated to serialize as a slim reference:

```java
// src/main/java/org/etsi/osl/controllers/tmf915/model/AiModel.java, around line 476
@JsonProperty("aiModelSpecification")
@JsonSerialize(using = AiModelSpecificationRefSerializer.class)
public @Nullable AiModelSpecification getAiModelSpecification() {
```

The annotation is `com.fasterxml.jackson.databind.annotation.JsonSerialize`, which belongs to Jackson 2. Spring Boot 4 serializes HTTP responses with Jackson 3 (`tools.jackson.*`), which does not read Jackson 2 databind annotations. The serializer is therefore ignored and the full specification is written. Annotations from `jackson-annotations` such as `@JsonProperty` and `@JsonIgnore` are shared by both versions and keep working, which is why nothing else looks broken.

Both Jackson versions are on the classpath (`jackson-databind-3.0.4` and `jackson-databind-2.20.2`).

This was reproduced by serializing one `AiModel` holding a specification with both mappers, against the built classes:

- `tools.jackson.databind.json.JsonMapper.builder().build()` wrote the full specification, including `specCharacteristic` and `modelDataSheet`.
- `new com.fasterxml.jackson.databind.ObjectMapper()` wrote `"aiModelSpecification":{"id":"spec-1","name":"n","version":"1"}`.

The existing test `testAiModelSpecificationSerializesAsReference` in `src/test/java/org/etsi/osl/controllers/tmf915/model/AiModelUnitTest.java` passes because it constructs a Jackson 2 `ObjectMapper` by hand. It does not cover the HTTP path.

Not verified: the running application was never called. That the HTTP layer uses Jackson 3 is inferred from Spring Boot 4 defaults and the jar contents. Task 1.2 confirms it.

## Part 1: fix the AiModel list (requested)

### 1.1 Port the reference serializer to Jackson 3

Files:

- `src/main/java/org/etsi/osl/controllers/tmf915/mappers/AiModelSpecificationRefSerializer.java`
- `src/main/java/org/etsi/osl/controllers/tmf915/model/AiModel.java`

Change the serializer to extend the Jackson 3 base class and change the import of `@JsonSerialize` in `AiModel` to `tools.jackson.databind.annotation.JsonSerialize`. The expected Jackson 3 names are `tools.jackson.databind.ValueSerializer`, `tools.jackson.databind.SerializationContext`, `tools.jackson.core.JsonGenerator`, and generator methods `writeStringProperty` / `writePOJOProperty` in place of `writeStringField` / `writeObjectField`. These names are from memory, so check them against the 3.0.4 jar before relying on them.

Keep the output fields as they are now: `id`, `href`, `name`, `version`, `@baseType`, `@schemaLocation`, `@type`, each omitted when null.

Search for other uses of Jackson 2 databind annotations in `src/main` (`@JsonSerialize`, `@JsonDeserialize` from `com.fasterxml.jackson.databind.annotation`) and port any that affect HTTP output.

### 1.2 Add a test through the real HTTP path

Add a MockMvc test for `GET /aiModel` (see `src/test/java/org/etsi/osl/controllers/tmf915/api/AiModelApiControllerTest.java` for the existing style) with a model whose specification has at least one `specCharacteristic` and a non-null `modelDataSheet`. Assert the response contains `aiModelSpecification.id` and does not contain `specCharacteristic` or `modelDataSheet`.

Write this test first and watch it fail before making change 1.1. A failure confirms the root cause; if it passes before the fix, stop and report, because the diagnosis is then wrong for the HTTP path.

Update `AiModelUnitTest.testAiModelSpecificationSerializesAsReference` to use a Jackson 3 mapper, since the Jackson 2 one will no longer see the annotation.

### 1.3 Build the reference without loading the specification

`aiModelSpecification` is `@ManyToOne(fetch = LAZY)`. After 1.1, the serializer calls `getName()` on the lazy proxy, which loads one full specification row per model (about 15 JSON TEXT columns each). For a list of N models that is N extra queries.

The `aim915_aim` row already stores what the reference needs, in the embedded `serviceSpecification` (`ServiceSpecificationRef`, columns `svc_spec_id`, `svc_spec_name`, `svc_spec_version`, `svc_spec_href`), which `AiModelRepositoryService.normalize` fills from the specification. That getter is `@JsonIgnore`.

Preferred approach: have the JSON `aiModelSpecification` property written from the stored reference fields when they are present, and only fall back to the entity when they are not. Getting the specification id from an uninitialized Hibernate proxy does not trigger a load, so `id` and a derived `href` (`/tmf-api/AiM/v4/aiModelSpecification/{id}`) are always available cheaply.

Acceptable alternative if that proves awkward: fetch the specification with the list in one query (`@EntityGraph` or `JOIN FETCH`). It removes the N+1 but still reads every specification's blobs.

Note that `normalize` currently skips an uninitialized specification (`Hibernate.isInitialized` check, an uncommitted change). Keep that behaviour; it exists so listing does not force a load.

Done when: listing N models issues no per-model query against `aim915_aimspec`. Check with `spring.jpa.show-sql` or Hibernate statistics in a test.

### 1.4 Honour `offset` and `limit`

`AiModelApiController.listAiModel(fields, offset, limit)` ignores all three arguments and calls `repoService.findAllAiModels()`, which returns every row. The Postman request sends `limit={{listLimit}}` to no effect.

Add paging to `AiModelRepositoryService` with a default limit of 50, matching `AiModelSpecificationRepositoryService.findAllAiModelSpecifications`. `AiModelRepository` already extends `PagingAndSortingRepository`.

Do not copy the specification service's offset arithmetic as is: `PageRequest.of(offset / size, size)` returns the wrong window when `offset` is not a multiple of `limit`. Use an offset-based `Pageable` (or fix both services the same way) and add a stable sort so pages do not overlap.

`findAllAiModels()` has other callers (`AiCatalogMcpTools`, `AiModelLifecycleService`). Keep an unpaged method for them or update them.

Implementing `fields` is optional for Part 1. If skipped, say so in the report.

### 1.5 Batch the characteristic load

`AiModel.serviceCharacteristic` is a lazy `@OneToMany` and is loaded during serialization, one query per model. Add `@BatchSize(size = 50)` on the collection, or set `spring.jpa.properties.hibernate.default_batch_fetch_size: 50` in `application.yml`. The global setting also helps `AiModelSpecification.specCharacteristic`.

## Part 2: database and persistence

Ordered by expected benefit. Each is independent.

1. **Specification list is heavy.** `GET /aiModelSpecification` returns every JSON TEXT column for each row plus a lazy `specCharacteristic` query per specification. Implement the `fields` query parameter, or return a light projection (id, href, name, version, lifecycleStatus, description, lastUpdate) for the list and keep the full entity for get-by-id. Changing the default list shape is an API behaviour change, so confirm with the owner before doing so.
2. **Null fields and compression.** The Jackson 3 output writes every null field. Set non-null property inclusion and `server.compression.enabled: true` with JSON in the mime types. Excluding nulls changes output on every endpoint and may break tests or clients that expect explicit nulls; check before applying.
3. **Missing indexes.** Add indexes on `aim915_aim(state)`, `aim915_aim(name)` and `aim915_aimspec(name, version)` via `@Table(indexes = ...)`. The schema is managed by `ddl-auto: update`. The last index serves `findByNameAndVersion`, which the MLflow sync calls per model.
4. **Open session in view.** `spring.jpa.open-in-view` is at its default (on), so lazy loads run during response serialization and hold a connection for the whole request. Set it to `false` and put `@Transactional(readOnly = true)` on read methods in the two `reposervices` classes. Do this after Part 1, since turning it off will surface any remaining lazy access as `LazyInitializationException`; the test suite should catch these.
5. **Converter cost on read.** About 25 columns across `AiModel` and `AiModelSpecification` use JSON `AttributeConverter`s (`mappers/converters`). Each is parsed on load, and Hibernate is believed to copy mutable converted values through the converter again for dirty checking. This second cost is an assumption; measure with a profiler before optimizing. Read-only transactions and projections on list paths are the cheap mitigation.
6. **Load-to-count.** `AiModelLifecycleService.deriveUniqueName` loads every model whose name starts with a prefix only to call `size()`. Replace with a `countByNameStartingWith` repository method.
7. **Payload logging.** `log.info("AiModel CREATE: {}", aiModelCreate)` and the equivalent in the specification service stringify whole objects at INFO on every create. Log ids and names, or move to DEBUG.

Notes for whoever continues:

- A `getId()` on a detached Hibernate proxy returns the id without loading it. This was checked with a throwaway test. `AiModelLifecycleService.enrichCharacteristicsFromSpecification` relies on it.
- Deployment code (`DeploymentScheduler.executeDeployment`, `executeUndeploy`, `AiModelLifecycleService.handleUndeploy`) runs inside its own `TransactionTemplate`, so it never depended on open-in-view. That template wraps the whole Docker build and deploy, which takes up to 10 minutes. For that whole time it holds one database transaction and one pooled connection. This is a performance problem in its own right: a few deployments at once can drain the Hikari pool (max 20). The fix is to load the model in a short transaction, deploy outside any transaction, then write the result in a second short transaction. ### Test configuration

`src/test/resources/application.yml` was replaced by `src/test/resources/application.properties`. A YAML file with the same name in test resources shadows the main `application.yml` on the classpath, so the tests ran without production settings and had to repeat them. A `.properties` file is loaded alongside the main YAML and takes precedence on conflicts. Tests therefore run with the real `application.yml`, overridden only for H2, `ddl-auto: create-drop`, the H2 dialect, and no MLflow (sync off, unreachable tracking URI). Profile files such as `application-integration.yml` still apply on top.

Consequences:

- `AiModelListHttpTest` and `ResponseCompressionTest` no longer repeat settings from `application.yml`. `open-in-view`, null exclusion and compression are now checked against the real file.
- MockMvc requests carry the real context path (`/tmf-api`), because `server.servlet.context-path` and `openapi.aiManagement.base-path: /AiM/v4` now apply.
- Integration tests (`@ActiveProfiles("integration")`) now also get the main `application.yml`. Before, they lacked `springdoc.oAuthFlow.*` and `jwt.jwk-set-uri`, which are required at startup, so they most likely could not start. A throwaway test confirmed that the integration-profile context now starts with the expected values (H2, `create-drop`, integration port range, main springdoc settings). The integration tests themselves were not run, because they need the remote MLflow and Docker hosts.

## Part 3: MCP tools, MLflow sync, webhooks

1. **MCP lookups scan everything.** In `mcp/AiCatalogMcpTools.java`, `getAiModel` loads all models and filters in memory, and `getAiModelSpecification` pages through all full specifications. Use `findAiModelById` and `findAiModelSpecificationById`.
2. **Classic-registry sync has no cache.** In `integrations/mlflow/MlflowSyncService.java`, `syncFromLoggedModels` keeps a synced set and a missing-artifact back-off; `syncFromClassicRegistry` does a database lookup and an artifact check for every version every 60 seconds. Apply the same two caches.
3. **Full MLflow fetch each cycle.** Every sync fetches all logged models. Filter by creation time since the last successful sync if the MLflow search API allows it, or lengthen `mlflow.sync.interval-ms`.
4. **Webhook delivery.** `integrations/hub/WebhookDispatcher.java` builds a `RestClient` with no connect or read timeout (its `timeout()` method is never used) and delivers to subscribers one after another. Add timeouts and deliver in parallel so one slow subscriber does not delay the rest.
5. **Async executor.** `@EnableAsync` is on with no explicit executor configuration. Define a bounded executor for webhook delivery.

## Part 4: findings from the documentation review

### 4.1 Webhooks never report deployment outcomes (high)

**Problem.** `AiModelDomainEvent`s are only published by `AiModelLifecycleService`, in response to API calls. State changes made in the background by `DeploymentScheduler` publish nothing:

- deployment completed: `reserved` → `active` (`MlflowModelService.updateModelAfterDeploy`);
- deployment failed: → `designed`, with a note (`DeploymentScheduler.executeDeployment`, catch block);
- automatic teardown at `endDate`: → `terminated` (`DeploymentScheduler.executeUndeploy`).

So a subscriber never learns that its model became `active`, which is the main reason to subscribe. The old integration guide's example (waiting for `active` in a webhook) could never fire.

**Fix.**

1. Inject `ApplicationEventPublisher` into `DeploymentScheduler`.
2. Publish `AiModelDomainEvent(model, STATE_CHANGE)` with the reloaded model after `executeDeployment` (state `active` or `designed`) and after `executeUndeploy` (state `terminated`).
3. Publish **after** the `TransactionTemplate` has committed, outside the lambda, so listeners never see uncommitted state.
4. Publishing is cheap when webhooks are disabled (no listener).

**Verify.** A unit test in the style of `DeploymentSchedulerTest` with a mocked publisher: one event per outcome, with the right state.

**Docs to update.** `docs/INTEGRATION_GUIDE.md`:

- section 4.3: polling no longer required;
- section 5, "Which changes produce an event": add the three background rows and remove the "send no event" paragraph;
- section 8, Limitations.

### 4.2 Docker Compose rejects every token on a new machine (high)

**Problem.** `docker-compose.yml` hard-codes `KEYCLOAK_ISSUER_URI` and `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI` to `http://172.16.100.94:8080/auth/realms/openslice`. `SecurityConfiguration.jwtDecoder()` accepts a token only if its `iss` equals that string exactly, and Keycloak sets `iss` from the URL it was called on. On any other machine every API call returns `401` until someone edits the file.

The `MLFLOW_*` defaults point at the same lab host, but those are already overridable with `${…:-…}`.

**Fix.**

- Make both issuer lines `${KEYCLOAK_ISSUER_URI:-http://localhost:8080/auth/realms/openslice}`.
- Consider the same `localhost` default for the MLflow and MinIO URLs, so the `full` profile works without exports.

**Verify.** On a fresh machine: `docker compose --profile full up -d --build`, get a token from `localhost:8080`, call `GET /tmf-api/AiM/v4/aiModel` and expect `200`.

**Docs to update.** `docs/USER_GUIDE.md` section 1.1 (becomes "set `KEYCLOAK_ISSUER_URI` if clients use another address") and the note under "Quick start" in `README.md`.

## Part 5: findings from the code review (2026-11-26)

### 5.1 Clients can make the server stop or delete any container on the Docker host (critical, security)

**Problem.** The undeploy path takes its Docker arguments from the model's `serviceCharacteristic`, and clients can write those characteristics:

1. `AiModelMapper.mergeServiceCharacteristics` (PATCH) and `AiModelMapper.fromCreate` (POST) accept any characteristic name, including the ones the deployer owns: `containerId`, `imageName`, `hostPort`, `endpoint`, `dockerHost`, `deployedAt`, `inferencePayloadExample`.
2. `MlflowDeployer.undeploy` runs `docker stop <containerId>`, `docker rm <containerId>` and `docker rmi -f <imageName>` with whatever is stored. It runs on `PATCH state=inactive`, on `DELETE /aiModel/{id}` and at `endDate`.
3. In the Compose setup the API mounts `/var/run/docker.sock`.

So any user with `ROLE_USER` can create a model with `platform=mlflow` and `containerId=<mysql container name>`, then delete it, and the server stops and removes the database container. The same works for Keycloak, the API container, or any image (`docker rmi -f`). No arbitrary command runs: `ProcessBuilder` does not use a shell. But the API can be used to take down everything else on the host.

`dockerHost` is a documented input (`INTEGRATION_GUIDE.md` section 4, `USER_GUIDE.md` section 5), so it cannot simply be made read-only. Today a client can point it at any Docker daemon, including a remote `tcp://` or `ssh://` one. The server then builds the image there, which sends the model artifacts it downloaded with its own S3 credentials to that daemon. `sanitizeDockerHost` only strips characters; it does not restrict the target.

**Fix.**

1. Treat `containerId`, `imageName`, `hostPort`, `endpoint`, `deployedAt` and `inferencePayloadExample` as server-owned. In `AiModelLifecycleService`, before `enrichCharacteristicsFromSpecification` runs (on PATCH it copies the stored characteristics into the update), drop them from `AiModelCreate` and `AiModelUpdate` input before mapping, or reject them with `400`. Rejecting is easier to diagnose; dropping is more compatible with clients that PATCH back a model they read. Recommendation: drop them and log at INFO. Only `MlflowModelService.updateModelAfterDeploy` may write them.
2. Label every container at `docker run` time (`--label tmf915.aiModelId=<id>`). Before `docker stop`/`rm`, check the label with `docker inspect --format '{{index .Config.Labels "tmf915.aiModelId"}}' <containerId>`, and skip with a warning if it does not match the model id. This also protects rows written before step 1.
3. Remove images only when no other model uses them (see 5.10); never `-f`.
4. Add `mlflow.docker.allowed-hosts` (list, default: just `mlflow.docker.host`). Reject a `dockerHost` characteristic that is not on the list with `400` at create/PATCH time, not at deploy time.

**Verify.**

- `AiModelLifecycleServiceTest`: a PATCH carrying `containerId` does not change the stored `containerId`.
- `MlflowDeployer` unit test: undeploy does not call `stopContainer` when the label check fails.
- Lifecycle test: create with a `dockerHost` that is not allowed returns `400`.

**Docs to update.** `docs/INTEGRATION_GUIDE.md` section 4 (`dockerHost` must be on the allow-list) and the table of output characteristics (read-only); `docs/USER_GUIDE.md` section 5 and section 8 (new setting).

**Outcome of PR 1 (steps 1 and 4).**

- **Step 1.** `AiModelLifecycleService.SERVER_OWNED_CHARACTERISTICS` lists the six names. They are removed from `AiModelCreate`/`AiModelUpdate` input at the start of `createAiModel` and `updateAiModel`, before `handleDeploy` copies stored characteristics, and logged at INFO (decision D1: drop and log).
- **Step 4.** New `PlatformDeployer.validateCharacteristics(List<Characteristic>)` (default no-op). The lifecycle service calls it for every deployer on create and on PATCH, so the lifecycle code stays platform-agnostic.
  - `MlflowDeployer` implements it with `mlflow.docker.allowed-hosts` (comma-separated; `mlflow.docker.host` is always allowed; empty or absent `dockerHost` is always allowed) and throws `IllegalArgumentException`, which gives `400`.
  - `MlflowDeployer.deploy` checks the stored `dockerHost` again, so rows written before the allow-list existed cannot deploy to other daemons.
- **Tests:**
  - `AiModelLifecycleServiceTest`: dropped on create and PATCH; the validation hook rejects.
  - `MlflowDeployerUnitTest` (new): allow-list parsing, matching, validation, deploy-time refusal.
  - `AiModelListHttpTest`: POST and PATCH through HTTP store no server-owned characteristic; a disallowed `dockerHost` gives `400` with the setting's name.
- **Docs updated:** `USER_GUIDE.md` sections 4, 7, 8; `INTEGRATION_GUIDE.md` 4.2, 4.4; `application.yml`.
- **Found while testing:** `POST /aiModel` requires `software` with at least one entry (bean validation, `400` with an empty body), so the deploy examples in the three guides would have failed. All three now include `"software": [{"id": "mlflow"}]`. The lifecycle code that adds `software` for `platform=mlflow` never runs on POST, because validation rejects the request first.
- **Client-visible:**
  - Server-owned characteristics in requests are ignored.
  - A `dockerHost` that is not allowed returns `400`. The Postman collection's deploy request sends `{{dockerHost}}`: set it to an allowed value or remove it.

### 5.2 Deploying a model can delete another model's container (high)

**Problem.** `MlflowModelService.generateContainerName` builds the container name from the model name and the specification version: `<name>-v<specVersion>`. Model names are not unique. A client can send any `name`, and the server-derived names can repeat too: `deriveUniqueName` appends `count + 1` of the existing models with the same prefix, so with models `…-1` and `…-2`, deleting `…-1` makes the next model `…-2` again. When `docker run --name X` fails, `MlflowDeploymentService.deployContainer` runs `docker rm -f X` and tries the next port. If X is the running container of another model with the same name, the first attempt fails with "name already in use", the cleanup force-removes the other model's container, and the second attempt succeeds. The other model stays `active` with an `endpoint` that no longer answers.

**Fix.**

- Always include the model id in the container name, for example `<name>-<first 8 chars of id>`. The id is unique, so names cannot collide.
- Make `deriveUniqueName` collision-free: retry with the next number while a model with that exact name exists, or append a short id.
- In the failure branch, remove only a container this attempt created: use the id `docker run -d` printed, or the label from 5.1. Never `rm -f` by name.

**Verify.** Unit test on `generateContainerName`: two models with the same name and specification get different container names. Unit test on the failure branch with a fake process runner (see 5.4): a failed `docker run` never calls `docker rm -f <name>`.

### 5.3 A failed `docker run` is retried on up to 4,001 ports (high)

**Problem.** `deployContainer` moves to the next port after *any* failure, not only "port is already allocated". If the image is missing, the daemon is unreachable, or the name is taken, it runs `docker run` once per port from 3000 to 7000. Each attempt can take up to `command-timeout-seconds` (30 s). Attempts that fail fast add up to minutes; attempts that time out add up to hours. The deployment thread, and the database transaction around it (Part 2 notes), are held for that long before the model is marked `designed`.

**Fix.**

- Retry the next port only when stderr contains `port is already allocated` or `address already in use`. Fail at once for any other error.
- Simpler alternative: publish with `-p 0:<containerPort>` so Docker picks a free port, then read it with `docker port <id> <containerPort>`. This removes the scan, but the host port is no longer limited to the configured range, which matters if a firewall only opens 3000 to 7000. Owner's choice; the first option keeps the current behaviour.

**Verify.** Unit test with a fake process runner: an "image not found" error makes exactly one `docker run` call.

### 5.4 Subprocess output is never drained, so long builds can stall (medium)

**Problem.** `buildImageFromUri` starts `mlflow models build-docker` and calls `waitFor(10, MINUTES)` without reading stdout or stderr. When a pipe's buffer fills (64 KB on Linux), the child blocks on write, and the build looks hung until the 10-minute timeout. Then the model goes to `designed` with "Build timed out". A Docker build with pip output easily exceeds 64 KB. `getContainerLogs` and `readMlmodelFromContainer` call `waitFor` before or between reads and have the same problem with large output. This has **not** been reproduced; it is the standard `ProcessBuilder` failure mode.

**Fix.** Extract one helper, `ProcessResult run(List<String> cmd, Map<String,String> env, Duration timeout)`. It merges stderr into stdout (`redirectErrorStream(true)`), drains output on a separate thread (or redirects it to a temp file), keeps the last ~64 KB for error messages, and kills the process on timeout. Use it for every Docker and MLflow command. Making the runner an injectable interface also enables the fake-runner tests in 5.2 and 5.3.

**Verify.** Test the helper with `sh -c 'head -c 2000000 /dev/zero; exit 0'`: it returns success well within the timeout.

### 5.5 Undeploy or delete during a running build leaves a container behind (medium)

**Problem.** `DeploymentScheduler.cancelScheduled` calls `future.cancel(false)`, which does not stop a deployment already running. If a client PATCHes `state=inactive` or deletes the model while the image is building:

- `handleUndeploy` finds no `containerId` yet, stops nothing, and sets `terminated`. The build then finishes, starts a container, and `updateModelAfterDeploy` sets the model back to `active`.
- On delete, the row is gone when the build finishes. The container keeps running on its port and nothing records it.

**Fix.** In `executeDeployment`, after `deployer.deploy` returns, re-read the model in a new transaction. If it no longer exists or is no longer `reserved`, undeploy the container just started and do not write `active`. Implement this as part of the transaction split in 5.6.

**Verify.** `DeploymentSchedulerTest` with a deployer that blocks on a latch: cancel while blocked, release, and assert `undeploy` was called and the state is not `active`.

### 5.6 Deployment errors can vanish, and the deployment holds a transaction for minutes (medium)

**Problem.**

- `executor.schedule(Runnable, …)` stores any exception in the returned future, and nobody reads it. If `executeDeployment` throws outside its own `try` (database unavailable, `UnexpectedRollbackException`, an exception in `findDeployer`), nothing is logged, the model stays `reserved`, and `scheduleUndeploy` is never called.
- The failure branch writes `designed` and the note in the same transaction as the failed deploy. If the deploy failed inside a joined `@Transactional` method, the transaction is already rollback-only, and the `designed` update is lost when it commits.
- The Part 2 notes already describe the other half: the whole build runs inside one `TransactionTemplate` and holds a pooled connection for up to 10 minutes.

**Fix.** Restructure `executeDeployment` and `executeUndeploy` as three steps:

1. A short read transaction loads the model.
2. The deploy runs outside any transaction.
3. A short write transaction records the result: `active`, or `designed` with the note.

Wrap each scheduled task body in `try/catch (Throwable)` that logs with the model id. `updateModelAfterDeploy` must then take the id and write in its own transaction rather than mutate the detached entity.

**Verify.** `DeploymentSchedulerTest`:

- A deployer that throws a `RuntimeException` leaves the model `designed` with a note.
- A repository that throws on the final write is logged and does not kill the executor.
- No transaction is active during `deployer.deploy` (`TransactionSynchronizationManager.isActualTransactionActive()` inside the fake deployer).

### 5.7 Webhook callbacks can target internal addresses (medium, only when webhooks are enabled)

**Problem.** `EventsSubscriptionApiDelegateImpl` stores any `callback` string. With `hub.webhook.enabled=true`, the server POSTs model payloads to it. An authenticated user can therefore make the server send requests to addresses only it can reach: `http://mysql:3306`, Keycloak's admin port, or cloud metadata at `169.254.169.254`.

**Verify.** Unit tests on the validator; a hub POST with `http://169.254.169.254/` returns `400`.

**Docs to update.** `docs/INTEGRATION_GUIDE.md` section 5.

### 5.9 Corrupt JSON columns read as empty and are saved back empty (medium)

### 5.13 PATCH accepts any state change, and a redeploy loses track of its container (high)

Added in a second review pass on 2026-11-26, confirmed by reading the code.

**Problem.** `AiModelLifecycleService.updateAiModel` only reacts to `reserved` and `inactive`; it never looks at the current state. `AiModelMapper.applyUpdate` writes any other requested state straight to the row.

- `PATCH state=active` marks a model active with no deployment. POST rejects this state; PATCH does not.
- `PATCH state=terminated` (or `designed`) on an active model changes the row and leaves the container running. The `endDate` teardown then skips it, because it only undeploys `active` models.
- `PATCH state=reserved` on a model that is already `active` or was deployed before starts a second deployment. `updateModelAfterDeploy` appends `containerId`, `imageName`, `hostPort` and `endpoint` with `addServiceCharacteristicItem`, which does not replace existing entries. The model then has two `containerId` characteristics, and `MlflowDeployer.getCharacteristicValue` returns the first, which is the old one. The next undeploy stops the old container (already gone) and leaves the new one running. Clients reading `endpoint` may also get the old value.

Redeploying an active model works today only by accident: the container name is the same, so the `docker rm -f` in 5.2 removes the old container. Once 5.2 is fixed, it would fail instead. Fix this item together with 5.2.

**Fix.**

1. Add a transition table in `AiModelLifecycleService` and reject anything else with `400`. Clients may request `reserved` (from `feasibilityChecked`, `designed`, `terminated`) and `inactive` (from `active`, `reserved`). `active` and `terminated` are set only by the server. Decide with the owner whether `reserved` on an `active` model means "redeploy" (undeploy first, then deploy) or is rejected; rejecting is simpler.
2. In `updateModelAfterDeploy`, replace server-owned characteristics by name instead of appending. On undeploy, remove `containerId`, `hostPort` and `endpoint` from the model so a terminated model does not advertise a dead endpoint.

**Verify.** `AiModelLifecycleServiceTest`: `PATCH state=active` returns `400`; `terminated` on an active model returns `400`. `MlflowModelService` unit test: two deploys of the same model leave exactly one `containerId` characteristic, the new one.

**Docs to update.** `docs/INTEGRATION_GUIDE.md` section 4 (allowed state changes) and `docs/USER_GUIDE.md` section 5.

**Outcome of PR 1 (step 1).**

- **Transition table.** `AiModelLifecycleService.CLIENT_TRANSITIONS` implements the table above. `checkStateTransition` runs at the start of `updateAiModel` and throws `IllegalArgumentException` (`400`) for anything else.
- **Redeploy.** `reserved` on an `active` model is rejected (decision D6).
- **Same state.** Requesting the model's current state is treated as no state change: the state is removed from the update and the other fields are applied. This keeps read-modify-write clients working, as D1 intends. Without it, PATCHing back an `active` model would fail.
- **Unknown model.** A state change on an unknown id is rejected (`400`, as other unknown-id errors on `aiModel` are today; see 4.4).
- **Tests:** `AiModelLifecycleServiceTest` (active, terminated, designed, reserved on active, inactive on designed, reserved from terminated, same-state, unknown id), `AiModelListHttpTest.patchToActive_returns400`.
- **Docs updated:** `USER_GUIDE.md` section 7; `INTEGRATION_GUIDE.md` 4.4.
- **Still open (PR 2):** step 2, replacing server-owned characteristics instead of appending them. Done in PR 2; see below.
